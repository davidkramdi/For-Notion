Journal de lab — SW-1 · IOS-XE · VRF-lite

Ça circule enfin

Trois switches, deux VRF, une seule ligne de départ : rd 65000:10, et rien d'autre. Ce carnet retrace, commande par commande, comment on est passé de « rien ne circule » à voir littéralement l'attribut RT attaché à une route réelle — avec les deux erreurs de syntaxe en cours de route, gardées telles quelles.

3 septembre 2026 Lab : SW-1 / SW-2 / SW-3, VRF-lite pur, sans MPLS, sans VXLAN VRF : VRF_USERS (65000:10) · VRF_GUEST (65000:20)
t0

Point de départ, confirmé sur SW-1 : vrf definition VRF_USERS / rd 65000:10. Pas de BGP, pas de route-target, pas de neighbor. La RD existe dans la config — elle n'est attachée à absolument rien.

1

Faire attacher la RD

Le minimum pour que BGP traite enfin une route pour cette VRF — sans neighbor, sans RT. Une seule variable à la fois.

SW-1 — enableconfig
SW-1(config)# router bgp 65000
SW-1(config-router)# address-family ipv4 vrf VRF_USERS
SW-1(config-router-af)#  redistribute connected
SW-1(config-router-af)# exit-address-family
SW-1 — enableshow
SW-1# show bgp vpnv4 unicast vrf VRF_USERS
BGP table version is 3, local router ID is 1.1.1.1
     Network          Next Hop            Metric LocPrf Weight Path
Route Distinguisher: 65000:10 (default for vrf VRF_USERS)
 *>   10.10.10.0/24    0.0.0.0                  0         32768 ?
 *>   10.10.100.0/30   0.0.0.0                  0         32768 ?
La RD est maintenant réellement attachée — en interne, 65000:10:10.10.10.0/24. Toujours rien dans la RIB (AD 0 du connecté bat toujours l'AD 200 du BGP) : ce n'est pas un échec, juste que seule la table BGP peut le montrer.
2

Retrouver la bonne syntaxe

Premier détour du carnet — la commande que j'avais donnée était fausse.

SW-1 — enableshow
SW-1# show bgp vrf VRF_USERS ipv4 unicast
                             ^
% Invalid input detected at '^' marker.
correction en direct

show bgp vrf X ipv4 unicast — syntaxe inventée, rejetée par le device.

Vérifié via la doc Cisco : le mot-clé après show bgp est vpnv4, pas ipv4 — même sans MPLS, parce qu'une route traitée par BGP pour une VRF devient en interne une route « VPNv4 ». Bonne commande : show bgp vpnv4 unicast vrf VRF_USERS.

3

Une deuxième table, symétrique

Même opération sur VRF_GUEST, pour avoir deux tables VPNv4 isolées avant d'y toucher.

SW-1 — enableshow
SW-1# show bgp vpnv4 unicast vrf VRF_GUEST
SW-1# --rien du tout
diagnostic

Table vide, sans même l'en-tête — signe que l'address-family n'existait pas du tout, pas juste une table sans routes. Confirmé par show running-config | section router bgp : la config de VRF_GUEST n'avait jamais été appliquée.

SW-1 — enableshow
SW-1# show bgp vpnv4 unicast vrf VRF_GUEST
BGP table version is 5, local router ID is 1.1.1.1
     Network          Next Hop            Metric LocPrf Weight Path
Route Distinguisher: 65000:20 (default for vrf VRF_GUEST)
 *>   10.10.20.0/24    0.0.0.0                  0         32768 ?
 *>   10.10.200.0/30   0.0.0.0                  0         32768 ?
Deux tables VPNv4 hermétiques, chacune avec son propre RD, aucune visibilité croisée. Le point de départ exact pour faire réellement circuler un RT.
4

Le RT réellement comparé

Un export d'un côté, un import de l'autre — le seul moment où RT sort du statut de ligne de config pour devenir un filtre actif.

SW-1 — enableconfig
SW-1(config)# vrf definition VRF_GUEST
SW-1(config-vrf)#  route-target export 65000:9999
SW-1(config)# vrf definition VRF_USERS
SW-1(config-vrf)#  route-target import 65000:9999
SW-1 — enableshow
SW-1# show bgp vpnv4 unicast vrf VRF_USERS
BGP table version is 7, local router ID is 1.1.1.1
     Network          Next Hop            Metric LocPrf Weight Path
Route Distinguisher: 65000:10 (default for vrf VRF_USERS)
 *>   10.10.10.0/24    0.0.0.0                  0         32768 ?
 *>   10.10.20.0/24    0.0.0.0                  0         32768 ?
 *>   10.10.100.0/30   0.0.0.0                  0         32768 ?
 *>   10.10.200.0/30   0.0.0.0                  0         32768 ?
correction en direct

« Les routes importées vont apparaître sous une section Route Distinguisher: 65000:20 séparée » — prédiction fausse, annoncée avant test.

Vérifié sur un cas quasi identique en forum Cisco : une route importée s'affiche sous le RD par défaut de la VRF qui l'accueille, jamais sous son RD d'origine — exactement ce que confirme la table ci-dessus : les 4 routes sont sous 65000:10, alors que 2 d'entre elles viennent de VRF_GUEST.

Version de table 5 → 7, nombre de routes 2 → 4 dans VRF_USERS. Le RT vient de faire un vrai travail de comparaison, pas juste d'exister dans la config.
✓

La preuve, jusqu'à la RIB et l'attribut lui-même

Deux vérifications finales : la route importée s'installe-t-elle réellement dans la table de routage, et peut-on voir l'attribut RT littéralement attaché à une route ?

SW-1 — enableshow
SW-1# show ip route vrf VRF_USERS
C        10.10.10.0/24 is directly connected, Vlan10
L        10.10.10.1/32 is directly connected, Vlan10
B        10.10.20.0/24 is directly connected, 00:03:52, Vlan20
L        10.10.20.1/32 is directly connected, Vlan20
S        10.10.30.0/24 [1/0] via 10.10.100.2
C        10.10.100.0/30 is directly connected, Vlan100
L        10.10.100.1/32 is directly connected, Vlan100
B        10.10.200.0/30 is directly connected, 00:03:52, Vlan200
L        10.10.200.1/32 is directly connected, Vlan200

Code B, sans concurrence d'une route connectée cette fois — donc BGP gagne et installe réellement la route. Détail à retenir : « is directly connected, Vlan20 » alors que Vlan20 appartient à VRF_GUEST. Aucune marque dans un paquet, nulle part — juste le FIB de VRF_USERS autorisé, par le RT, à pointer vers l'interface d'une autre VRF.

SW-1 — enableshow
SW-1# show bgp vpnv4 unicast vrf VRF_USERS 10.10.20.0
BGP routing table entry for 65000:10:10.10.20.0/24, version 6
Paths: (1 available, best #1, table VRF_USERS)
  Local, imported path from 65000:20:10.10.20.0/24 (VRF_GUEST)
    0.0.0.0 (via vrf VRF_GUEST) (via VRF_GUEST) from 0.0.0.0 (1.1.1.1)
      Origin incomplete, metric 0, localpref 100, weight 32768, valid, external, best
      Extended Community: RT:65000:9999
« imported path from 65000:20:… (VRF_GUEST) » retrace l'origine ; « Extended Community: RT:65000:9999 » est l'attribut RT littéralement attaché à cette route. C'est la preuve la plus directe possible sans capture réseau.
reste à confirmer

ping vrf VRF_USERS 10.10.20.1 source Vlan10 — pour boucler jusqu'au trafic réel.
